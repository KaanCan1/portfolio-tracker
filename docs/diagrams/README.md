# Diagrams — sources and style rules

This folder holds the **sources** for the two diagrams the README embeds. The PNGs
are derived output: edit the HTML, then re-export the PNG.

| file | what it shows | where it appears |
|---|---|---|
| `architecture{,-dark}.html` | data flow: providers → server → pure modules → dashboard | README, *Architecture* |
| `measurement-pipeline{,-dark}.html` | risk pipeline: bars → alignment → Cholesky → Monte Carlo → breach test | README, *Measurement discipline* |

Each diagram is a single self-contained HTML file with inline SVG — no build step,
no external assets. GitHub swaps the light and dark PNGs via `<picture>` and
`prefers-color-scheme`, so both variants must stay in sync.

## How they are produced

Drawn with the [`cathrynlavery/diagram-design`](https://github.com/cathrynlavery/diagram-design)
skill (MIT), which is installed externally rather than vendored — a checked-in copy
would silently drift from upstream. **That is why the rules below live here** instead
of in the tool's own profile: the tool is replaceable, the decisions are not.

PNG export uses headless Chrome:

```bash
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" \
  --headless --screenshot=out.png --force-device-scale-factor=2 \
  --window-size=1400,900 --default-background-color=FFFFFF diagram.html
```

Known deviation: the skill expects Playwright, and this route cannot produce a
transparent background — the PNGs ship with an opaque one. That is fine for the
`<picture>` swap, but **anything that relies on transparency will need Playwright.**

## Tokens come from the dashboard, not from taste

The diagrams do not invent a palette. Every color maps to a variable in the
dashboard's own `:root` block (`public/style.css`), so a diagram cannot drift away
from the product it describes.

| role | CSS var | light | dark | uses |
|---|---|---|---|---|
| `paper` | `--bg` | `#f6f5f1` | `#16211a` | 32 / 45 |
| `ink` | `--ink` | `#12140f` | `#f2f0e9` | 28 / 28 |
| `muted` | `--muted` | `#5f6457` | `#c9cfc4` | 62 / 47 |
| `soft` | `--ink-soft` | `#6e7366` | `#8a978c` | 16 / 31 |
| `accent` | `--accent` | `#1b6a40` | `#66c99a` | 19 / 19 |
| `link` | `--sky-d` | `#46688a` | `#7fa8cd` | 7 / 7 |
| `rule` | hairlines | `rgba(18,20,15,α)` | `rgba(242,240,233,α)` | 22 / 22 at α=0.12 |

Two further roles (`paper-2`, `rule-solid`) exist in the skin but **are not used by
these two diagrams** — listing them as if they were would misdescribe the files.

### Why the accent is green

The product's design language says *color only where action is required*, and
`--accent` is marked as the single accent. Red is reserved for real loss or risk.
Promoting red to the focal color in a diagram would break that distinction
everywhere else. The darker `--brand #0e5236` was tried and rejected: on warm paper
it sits too close to `ink`, and the "this is the focal element" signal disappears.

## Two dark-mode rules, found by measuring

Both were found **after** the diagrams were drawn, by looking at the exported
output. What is true in light inverts in dark.

**1. The dark accent must be saturated.** The first attempt was `#a9d8bf`, the
quote color from a slide deck. It failed: in dark, `muted` rises to near-white, and
a pale green next to it recedes — **the eye goes to the non-focal arrows and the
emphasis inverts.** `#66c99a` keeps the brand hue while separating from the grays.
In text contexts `#a9d8bf` is still correct; this rule is only about diagram accent.

**2. In dark, arrow strokes use `soft`, not `muted`.** Strokes only — sublabel
*text* stays `muted`, or legibility drops. One token, two jobs, and they diverge in
the dark.

The shared lesson: **contrast is relative, not absolute.** In light the accent is
the darkest thing on the page and stands out for free; in dark the lightest thing
is `muted`, and the accent has to compete with it. This is why a dark variant
cannot be generated by inverting colors — that the focal element is *still* focal
has to be confirmed by eye.

The same pressure shows up in the fills. The inversion rule
(`rgba(18,20,15,α)` → `rgba(242,240,233,α)`, same α) holds exactly for 12 of the 15
opacity levels in use, including every hairline. The exceptions all move one way:
the faintest wash goes `0.018 → 0.025`, and the opaque `#ffffff` node fill of the
light variant becomes a translucent `rgba(242,240,233,0.06)` in dark. Faint things
wash out against dark paper, so they need a little more.

## Label-mask geometry

Labels sitting on a connector draw a `paper`-colored rectangle behind themselves to
erase the line underneath. **Width is computed from the text — never hard-coded.**

This bit once: the English label `THRESHOLD` is longer than the label it replaced,
and its mask overlapped a node by 7×12px. Because nodes are painted *after* labels,
the mask is hidden and the text renders as a fragment sitting on the node's border.
The rule is to place the label on a stretch of connector that runs through open
canvas — for a connector leaving a node's right edge, clear that node's
`x + width` before the mask begins.

**This gate is not automatic.** The skill's docs reference a geometry checker that
ships only with the tool's own source repository; the installed skill provides
`self_check.py` (accessibility and single-file rules), which does not test for
overlap. Verify mask width by eye when adding or translating a long label.
